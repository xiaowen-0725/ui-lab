## 已验证能力

- UI Lab 已有可发现的 Catalog、registry source family、Theme Kit、Recipe、System Preset、项目 binding 与 strict Audit 契约。
- Greenfield fixture 能用独立 Vite / React 19 / Tailwind CSS 4 工具链完成 lint、strict typecheck、unit test、production build、strict Audit 与 Playwright E2E。
- Greenfield strict Audit 达到 `0 errors / 0 warnings`，所需 source family exact；三档 viewport、light / dark、关键状态、键盘、字体、overflow 与 reduced-motion 场景已有自动化覆盖。
- Assembly Studio 已能解析选择、生成 Draft、展示固定 candidate matrix，并区分 calibration source、candidate regression capture 与 approved acceptance evidence。
- Confirmed Manifest 的服务与 schema 会阻止 pending candidate、自洽 hash 或缺少可信 Catalog / visual acceptance 的输入绕过确认门禁。
- 当前 8 张视觉图有稳定 fixture 与候选证据记录，可用于当前实现的回归检查。

## 目前不能证明

- 不能证明当前 Workbench 或 Parking Agent 与 Codex 视觉一致，因为没有用户批准的 acceptance master。
- 不能证明正常 motion personality；Assembly preview 全局强制 reduced motion，只覆盖静态降级路径。
- 不能证明 capture readiness 在首次 viewport 与 HMR 条件变化下稳定，现有准备信号仍有时序敏感性。
- 不能证明已发布 npm CLI 与仓库源码能力一致；公开版本与源码版本存在差距。
- 不能证明 Parking Agent 已具备可执行 adopt 输入；frontend package root、binding 与保留契约尚未锁定。
- 不能由 1 个 System Preset 和 2 个 Recipes 推导出对更多应用形态的成熟覆盖。

## Top issues

1. **`/studio` 默认语言存在 307 自循环。** 默认 locale 入口可返回到自身，阻断稳定的首次运行与自动化访问。
2. **8 张图全部仍是 candidate / pending。** 没有 approved acceptance master，因此不能产生有效 fidelity 结论，也不能解锁依赖用户视觉批准的 checkout / confirmation。
3. **Preview 全局 `reducedMotion="always"`。** 当前只能验证 reduced-motion 降级，不能验证正常 motion、节奏与交互连续性。
4. **Capture readiness 对首次 viewport / HMR 敏感。** 初始布局稳定、字体就绪和双 animation frame 信号在热更新或首个 viewport 下仍可能产生竞态。
5. **npm CLI `0.1.1` 落后于源码 `0.3.0`。** benchmark 必须明确使用已发布 CLI 还是仓库源码，不能把源码能力归给旧 npm 包。
6. **`APPLICATION_KIT.md` 对 Phase 2 checkout 的表述落后代码。** 文档与当前 Studio / service 能力需要重新对齐，避免把已实现和未获证据批准混为一谈。
7. **Parking frontend root / package root 有歧义，当前分支没有 binding。** 在真实 root、`components.json`、`ui-lab.config.json`、lock 与保留范围确定前，采用工作必须保持 Block。
8. **应用级覆盖面仍窄。** 当前只有 1 个 System Preset 与 2 个 Recipes，尚不足以证明跨产品类型的稳定复用。

## 场景判定

### A — Platform maturity: 64 / 100

Catalog、Skill、CLI 与应用契约已经形成可运行骨架，Greenfield 路线有真实 fixture；但发布版本、文档、视觉批准和应用覆盖仍不完整。结论保持 `Insufficient evidence`，不能因为静态资产数量较多就升级为成熟。

### B — Greenfield Workbench: 86 / 100

Static 与 Runtime 通过，达到 Greenfield 的 ≥85 门槛、strict Audit 0/0、source-family exact 和 E2E 全过。Visual 因缺 approved reference pair 保持 pending / insufficient，Human 未批准；不得称为 Codex fidelity pass。

### C — Assembly Studio visual pipeline: 75 / 100

订单、候选矩阵和证据角色已有实现，但 `/studio` 307、capture readiness 与全局 reduced motion 使 Runtime / evidence 为 Block。8 张 pending candidate 不能证明 fidelity，因此视觉结论是 `Insufficient evidence`。

### D — Parking adopt readiness: 40 / 100

当前分支无法确定真实 frontend package root，也没有可验证的 UI Lab binding。业务状态、IPC/API、路由、自动化选择器与现有视觉保留范围尚未形成 adopt contract；在这些输入补齐前不得修改 Parking 前端。

## 下一轮基线条件

下一轮应保留同一 rubric 和场景边界，并优先补齐：稳定 `/studio` 入口、正常 / reduced motion 双路径、capture readiness 时序、用户批准的 acceptance master、npm CLI 发布一致性、Parking binding，以及新增 Preset / Recipe 后的独立场景验证。
